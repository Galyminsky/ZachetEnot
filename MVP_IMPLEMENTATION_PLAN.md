# План минимальной реализации MVP ZachetEnot

План построен по фактическим пакетам проекта; архитектуру не перестраивает. Каждый этап имеет проверяемый результат. Сборка/тесты — владелец в Android Studio в соответствии с проектными правилами.

## Этап 0. Восстановить проверяемую среду

**Изменения:** вне приложения: настроить Android Studio/Gradle Wrapper так, чтобы он мог создать Gradle user home lock-файл; повторить `:app:testDebugUnitTest`. Разобрать известные ошибки `DataStoreProgressRepositoryTest` на временном файле. Исходники не переписывать до получения повторяемого результата.

**Результат:** сохранён свежий лог успешной конфигурации и список тестовых падений; после исправления два ранее падавших теста проходят и весь модульный набор зелёный.

## Этап 1. Зафиксировать контент и семантику попытки

**Изменения:** получить/использовать существующий аудит матрицы 2.0; определить A–H coverage и те форматы заданий, которые нужны в первом срезе. Решить, продолжается ли попытка после закрытия процесса или сбрасывается по уже принятому правилу журнала. Не генерировать новые учебные вопросы в рамках технической адаптации.

**Результат:** короткая утверждённая спецификация формата MVP, достаточного банка и lifecycle; к каждому обязательному типу заданий привязаны данные и способ проверки. Открытые вопросы аудита сняты.

## Этап 2. Первый сквозной путь на существующей архитектуре

**Изменения:** использовать текущие `ContentRepository`, `ProgressRepository`, domain engine и Compose экраны. Добавить минимальный app composition root/state holder (ViewModel, если это уже принятый способ этапа 2B) и навигацию: темы → подготовка → попытка. Подключить ошибки загрузки/пустой контент и обработку ответа/таймера. Никаких DI framework/Room без обоснования.

**Результат:** из launcher Activity открывается локально загруженная тема; доступна подготовка; начинается попытка с правильным числом вопросов; ответ фиксируется один раз; таймер завершает её; экран результата показывает pass/fail. Ни один экран не питается preview hardcode.

## Этап 3. Записать завершённые попытки и показать разбор

**Изменения:** добавить минимальную локальную модель `Attempt`/`QuestionResult`, репозиторий, сохранение результата и список истории. Записывать attemptId, topicId, contentVersion, начало/конец, elapsedMs, completionReason, вопросы, ответы и правильность. Не сохранять имя или иные персональные данные. Вывести локальную историю и ошибки/объяснения. Выбор хранилища основывать на объёме и атомарности; прогресс оставить в текущем DataStore.

**Результат:** после завершения попытка остаётся после перезапуска; в истории видны дата/результат/время; разбор показывает ошибку на вопросе и объяснение нужного правила. Unit-тестами подтверждены round-trip и случай пустых/прерванных данных.

## Этап 4. Политика восстановления и контентная совместимость

**Изменения:** реализовать только выбранную семантику: либо snapshot сессии и дедлайн для resume, либо детерминированный сброс сессии при закрытии. Присвоить JSON `schemaVersion` и `contentVersion`; расширить валидатор минимальными проверками ссылок и уникальности сущностей. Подключить поддерживаемые типы согласно утверждённому матричному scope.

**Результат:** закрытие/возврат ведёт себя воспроизводимо; старый/некорректный JSON даёт понятную ошибку; фиксированная версия контента сохраняется с попыткой; по каждой A–H записи есть проверяемый статус покрытия.

## Этап 5. MVP debug-проверка

**Сценарии:** чистый запуск без сети; загрузка курса; тест ровно из 15 вопросов; корректный/неверный ответ каждого включённого типа; лимит времени и предупреждение; проходной 14/15 и непроходной результат; новая неограниченная попытка; сохранение истории; закрытие/восстановление по принятой политике; разбор ошибок; сбой/пустой content asset.

**Результат:** `assembleDebug` успешен в Android Studio; все unit tests успешны; ключевой сценарий пройден на целевом устройстве/эмуляторе; зафиксированы устройство/API, версия debug сборки и результаты сценариев. До этих подтверждений проект не помечать как протестированный MVP.

## После MVP

Полировка планшетной раскладки, казахский язык, остальные предметы/классы, облачная синхронизация, аналитика и персонализация — только после обратной связи учителей и отдельного решения.
