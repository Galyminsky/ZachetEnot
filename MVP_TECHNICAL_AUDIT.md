# ZachetEnot — технический аудит MVP

Дата аудита: 2026-11-03. Область: текущая рабочая копия Android-проекта. Метод: чтение исходников, ресурсов, JSON, Gradle-конфигурации, тестовых отчётов и документации; исходный код и учебные данные не менялись.

## Резюме

Проект содержит полезное ядро предметной логики (выбор вопросов, сессия, таймер, прогресс), загрузку JSON из assets, DataStore для отметок пройденных тем, Compose UI Kit и статические макеты основных экранов. Эти части пока не составляют приложение: `MainActivity` отображает шаблонный Greeting, а создание репозиториев, навигация и связь UI с доменом отсутствуют. Сборка в текущей среде не подтвердилась: Gradle Wrapper завершился до Gradle из-за невозможности создать lock-файл в `C:\.gradle`. Имеющийся отчёт тестов от 2026-11-02 показывает 54/56 успехов, две ошибки DataStore.

Следующий практический шаг: устранить средовой блокер запуска Gradle и воспроизвести известные два падения теста; параллельно начать минимальную интеграцию потока «каталог → подготовка → попытка → результат/разбор» после решения владельца по поведению восстановления попытки и содержанию банка. Этот отчёт не объявляет приложение готовым к тестированию учителями.

## A. Что уже существует

- Один Android-модуль `:app`, Kotlin, Compose Material 3; `applicationId`/namespace `com.galyaminsky.zachetenot`, minSdk 29, compile/target SDK 37. Java compatibility 11; Gradle daemon toolchain 17.
- Чистые доменные модели для тем, правил, вариантов и вопросов. У вопроса проверяются минимум два варианта, уникальные ID вариантов, наличие правильного варианта и непустой текст.
- `TestEngine` выбирает 15 случайных элементов без повторного выбора индекса из входного списка и перемешивает варианты. `TestSession` фиксирует правильность ответа по ID, считает ошибки по правилам и допускает завершение сессии; `TestTimer` отсчитывает 20 минут и выдаёт предупреждения на 5 и 1 минуте. Есть `BackgroundGuard` с порогом более 60 секунд.
- `ContentParser` преобразует JSON DTO в domain и проверяет ссылки вопроса на тему/правило и уникальность ID вопросов. `AssetContentRepository` загружает файл из `assets` на IO dispatcher.
- `DataStoreProgressRepository` сохраняет только набор ID пройденных тем и умеет сброс. `ProgressCalculator` вычисляет статусы/проценты.
- Compose-компоненты, UI-модели и preview-экраны подготовки, теста, результата и разбора ошибок. Экран теста визуально предусматривает четыре формы ответа.
- Unit-тесты для большей части доменных классов и парсера существуют; instrumented test является шаблонным.
- Манифест не запрашивает интернет-разрешение; контент поставляется локальным asset. Учётной записи/серверного клиента в проекте не найдено.

## B. Фактическая архитектура

Слои представлены пакетами, но интеграция между ними отсутствует. `domain` содержит модели, правила тестирования и контракты репозиториев; `data` содержит asset-парсер и DataStore-реализацию; `ui` содержит библиотеку компонентов и презентационные composable. ViewModel, app-level composition root, навигационный host и экран каталога тем в исходниках не найдены. `MainActivity.kt` напрямую рендерит `Greeting("Android")`.

Существующий вариант хранения прогресса — Preferences DataStore, не Room/SQLite. Он подходит текущему множеству пройденных тем. Он не хранит сессию, ответы, результат либо историю. Переписывать архитектуру или вводить Room на этапе аудита оснований нет. При добавлении истории нужно выбрать простейшее локальное хранилище, которое гарантирует атомарную запись полного результата; для растущей истории структурированная БД станет обоснованной, но не обязательна до уточнения требований.

Ошибка JSON/IO из `AssetContentRepository` не преобразуется в UI-состояние: вызывающей интеграции пока нет. Нет контентной версии, версии схемы, миграции или импорта/обновления набора во время работы приложения. Сейчас обновление — замена asset вместе с новой сборкой.

## D. Контент и данные

Текущий `russian_grade3.json` успешно читается PowerShell `ConvertFrom-Json`: 6 тем, 3 правила, 144 записи вопросов; по 24 записи на тему и по 48 на правило. Структурные поля содержат topicId, ruleId, варианты и correctOptionId. По форме все вопросы — выбор из вариантов. Идентификаторы вопросов уникальны по проверке парсера; варианты проверяются внутри модели вопроса.

Ограничения: журнал называет этот массив временным; в нём 24 вопроса на тему, тогда как движку нужно 15 на попытку, поэтому по одному лишь объёму остаётся мало вариативности. Часть тематических вопрос-копий относится к тому же общему набору трёх правил — требуется содержательная проверка владельцем/редактором контента, но новый аудит учебников здесь не выполнялся. Уникальность ID тем и правил, непустые поля правил/вариантов, ровно один корректный ответ как семантический факт, дубли по смыслу и покрытие плана A–H отдельными валидаторами не проверяются.

Схема не имеет `contentVersion`/`schemaVersion`. JSON импортируется только из packaged asset; механизма обновления контента на устройстве нет. Доменные `Question` и `Option` поддерживают только выбор варианта. Экраны UI содержат заготовки ввода текста, последовательности и сопоставления, но domain, JSON DTO, парсер, проверка ответа, результат и разбор этих форм не поддерживают. Документы/файлы аудита матрицы 2.0 в доступном дереве проекта не обнаружены; соответствие направлению A–H поэтому помечено `not_verified`, матрица не реконструировалась.

## E. Логи и аналитика

Не сохраняются начало/завершение попытки, выбранные вопросы, ответы, правильность по вопросу, длительность, прерывания/восстановление и версия контента. `TestSession` хранит только булеву правильность в памяти; `TestResult` — агрегаты по правилу. Логирование ошибок приложения и локальный диагностический журнал не найдены. Персональных данных учащегося не требуется.

Минимальная локальная запись для MVP: `attemptId` (UUID), `topicId`, `contentVersion`, `startedAt`, `finishedAt`, `elapsedMs`, `completionReason` (submitted/timeout/interrupted), итоговые `correctCount/totalCount/passed` и массив `questionResults` с `questionId`, `selectedOptionId` nullable и `isCorrect` nullable/вычисляемым. Для объяснений связывать ошибку с ruleId из неизменяемого контента соответствующей версии. Сохранять без имени, почты или идентификатора ученика. Для продолжения после закрытия дополнительно нужен снимок незавершённой сессии (ID/порядок вопросов, текущий индекс, ответы и дедлайн); если сохраняется принятое в журнале правило сбрасывать попытку при закрытии, snapshot не нужен и UI должен явно реализовать сброс.

## F. Проверки и ограничения среды

- JSON: успешно разобран командой PowerShell `ConvertFrom-Json`; количество сущностей и распределение вопросов проверены.
- Сборка/тесты в рамках этого аудита не завершены. Попытка `gradlew.bat :app:testDebugUnitTest` прекратилась до запуска Gradle: Wrapper не смог создать `C:\.gradle\wrapper\dists\...zip.lck` (доступ к системному каталогу). SDK указан в `local.properties` (`C:\Users\Galyaminsky\AppData\Local\Android\Sdk`), Java 17 доступна; факт установленного/рабочего SDK этой попыткой не проверялся.
- В проекте имеется прежний XML-отчёт `app/build/test-results/testDebugUnitTest`, timestamp 2026-11-02: 56 тестов, 54 прошли, 2 упали в `DataStoreProgressRepositoryTest` на IOException переименования временного файла. Это исторический результат, не текущий повторный прогон.
- `app/build/outputs/apk/debug/app-debug.apk` существует как ранее созданный артефакт, но не доказывает, что текущие исходники собираются.
- Эмулятор/устройство не запускались. Повторный OCR/аудит учебников не выполнялся.

## G. Категории готовности

### A — Уже готово по коду

- Базовая логика выбора 15 элементов, проверки выбранного optionId, подсчёта результата и порога 14/15: `domain/test/TestEngine.kt`, `TestSession.kt`, `domain/model/TestResult.kt`, `TestConfig.kt`.
- Парсер/локальная загрузка контента и валидирование ссылок: `data/ContentParser.kt`, `AssetContentRepository.kt`.
- Локальное хранение пройденных тем и расчёт прогресса: `DataStoreProgressRepository.kt`, `ProgressDataStore.kt`, `domain/progress/*`.
- Compose UI-компоненты и статические макеты: `ui/components/*`, `ui/screens/test/*`, `ui/screens/result/*`.
- Только кодовая готовность; сквозная работоспособность не подтверждена.

### B — Требует исправления или решения

- `MainActivity.kt`: шаблонный экран, не показывает продуктовые экраны.
- Существующий прогон: два падения DataStore теста (`DataStoreProgressRepositoryTest.kt`, XML отчёт от 2026-11-02); воспроизвести и исправить после восстановления Gradle-среды.
- `TestSession` не хранит выбранный optionId, поэтому построить детальный разбор невозможно только из результата.
- Модель/парсер поддерживает только multiple choice; UI-заготовки дополнительных типов не имеют рабочего домена.
- Нужны обработка ошибок загрузки, lifecycle, timer expiry, exit flow и интеграция состояний экранов.
- Требуется разрешить противоречие «восстановить состояние после закрытия» против записанного ранее «закрытие приложения сбрасывает попытку».
- `targetSdk 37` и версии AGP/Gradle/Kotlin зафиксированы в проекте, но совместимость данной комбинации этим аудитом сборки не проверена.

### C — Нужно для MVP

- Встроить репозитории и доменную логику через простой app-level composition root; добавить ViewModel/state holder и навигацию между готовыми экранами.
- Реализовать сохранение результата и историю, а также согласованный lifecycle выбранной политики продолжения/сброса.
- Закрыть банк реального контента: как минимум 15 разных вопросов на доступную тему (практически желательно существенно больше); не считать имеющиеся 24 тематические копии достаточным разнообразным банком.
- Зафиксировать формат A–H по доступным материалам матрицы 2.0 и определить, какие типы заданий входят в MVP; лишь затем расширять модель JSON/валидацию/проверку ответов.
- Обработать ошибки/пустой контент и связать итог с просмотром ошибок/объяснений.
- После настройки Gradle среды получить подтверждённую debug-сборку и зелёный тестовый прогон; проверить основные сценарии на устройстве.

### D — После MVP

- Удалить шаблонные `Greeting`/`ExampleUnitTest` и неиспользуемые превью/ресурсы после проверки ссылок и только отдельной задачей.
- Динамическое скачивание/обновление банка, синхронизация, серверная аналитика, учётные записи, персональная аналитика.
- Казахская локализация, остальные классы/предметы, планшетная адаптация и расширенные настройки, если не нужны для первой учительской проверки.
- Room, DI-фреймворк, сложная архитектурная перестройка — только если рост данных и интеграции покажет необходимость.

## H. Рекомендуемое продолжение

Сохранить текущие пакеты domain/data/ui и Preferences DataStore для прогресса. Сначала добиться воспроизводимого Gradle запуска и устранить два известных тестовых падения. Затем согласовать одну развилку: восстановление незавершённой попытки или сброс после закрытия. После этого выполнить тонкую интеграцию: root создаёт `AssetContentRepository`, `DataStoreProgressRepository`, engine/timer; экранный state holder загружает тему и строит UI state; навигация связывает уже существующие Compose-экраны; завершение атомарно записывает результат. Историю начинать с небольшой локальной модели без персональных данных; выбирать БД только если выбранное хранилище DataStore не обеспечивает требуемую атомарность/объём.

Не расширять типы заданий и банк до получения/проверки доступных материалов матрицы 2.0. Для каждого этапа фиксировать проверяемый результат и запускать Gradle/устройство владельцем в Android Studio, если среда агента останется недоступна.
